Este guia é sobre o uso do Claude **no chat** (web, desktop ou celular) para trabalhar com código: entender um trecho que você herdou, revisar um pull request antes de pedir aprovação, achar a causa de um erro ou escrever testes. Você cola o código, o Claude responde, e quem decide o que entra no projeto é você. Se o que você procura é uma IA que abre o repositório, edita arquivos e roda comandos sozinha, o caminho é o Claude Code, explicado no [guia do Claude Code no terminal](/artigos/claude-code-terminal-guia). Se ainda não conhece a ferramenta, comece pelo [guia sobre o que é o Claude](/artigos/o-que-e-claude-anthropic).

## Chat ou Claude Code: qual usar

As duas formas usam a mesma família de modelos (o modelo padrão de cada uma pode ser diferente), mas resolvem problemas diferentes.

| Situação | Chat do Claude | Claude Code |
|---|---|---|
| Entender um trecho de código ou um conceito | Ideal | Funciona, mas é mais do que o necessário |
| Revisar uma função ou um diff colado | Ideal | Bom, se o código já está no repositório |
| Depurar um erro com stack trace | Bom | Melhor quando o bug envolve vários arquivos |
| Implementar uma funcionalidade em um projeto existente | Trabalhoso: você copia e cola tudo | Ideal: lê o projeto e edita os arquivos |
| Rodar testes e comandos | Só no ambiente de execução do próprio Claude, sem acesso ao seu projeto | Roda no seu ambiente, com sua permissão |
| Plano necessário | Free, Pro, Max, Team, Enterprise | Pro, Max, Team, Enterprise ou chave de API |

Segundo a [documentação oficial](https://code.claude.com/docs/en/overview), o Claude Code é "an agentic coding tool that reads your codebase, edits files, runs commands, and integrates with your development tools". No chat, nada disso acontece no seu computador: o Claude só vê o que você colar ou anexar.

## Antes de começar: ajustes que fazem diferença

1. **Escolha o modelo.** O Sonnet 5 é o padrão dos planos Free e Pro, conforme o [anúncio da Anthropic](https://www.anthropic.com/news/claude-sonnet-5). Nos planos pagos, dá para trocar para o Opus 5.5 no seletor, o que ajuda em problemas de lógica mais difíceis. O mesmo seletor permite ajustar o nível de esforço.
2. **Ative a execução de código**, se quiser que o Claude rode scripts de teste no ambiente de execução dele (sem acesso ao seu computador). O recurso existe em todos os planos e, no Free, Pro e Max, é ligado em Settings > Capabilities.
3. **Use Projects para contexto fixo.** Se você sempre trabalha no mesmo sistema, crie um projeto com o guia de estilo do time, o esquema do banco e as convenções de nomes. Veja como no [guia do Claude Projects](/artigos/claude-projects-como-usar).
4. **Tire segredos do código antes de colar.** Troque chaves de API, senhas, tokens e dados de clientes por valores falsos como `SUA_CHAVE_AQUI`.

## Prompts prontos para copiar

Os prompts abaixo funcionam melhor quando você troca os trechos entre colchetes pelas informações reais do seu projeto. Todos são exemplos: adapte a linguagem e o nível de detalhe.

### Explicar código que você não escreveu

```text
Sou desenvolvedor [júnior/pleno/sênior] e acabei de assumir este código.
Linguagem: [Python 3.12 / TypeScript / PHP 8...]. Framework: [Django / Next.js / Laravel...].

1. Explique em 3 frases o que este trecho faz.
2. Depois, explique bloco a bloco, sem repetir o código inteiro.
3. Aponte dependências externas e efeitos colaterais (banco, rede, arquivos, variáveis globais).
4. Liste o que não dá para saber só por este trecho e que eu deveria verificar no resto do projeto.

[cole o código]
```

O item 4 é o que evita a armadilha mais comum: a IA "completar" com suposições aquilo que está em outro arquivo.

### Revisar código antes do pull request

```text
Faça um code review deste diff como um revisor sênior exigente.
Contexto: [o que a mudança deveria fazer].

Organize a resposta em:
- Bugs ou comportamentos incorretos (com a linha e o porquê)
- Riscos de segurança (injeção, validação de entrada, dados sensíveis em log, permissões)
- Casos de borda não tratados
- Legibilidade e nomes
- O que está bom e não deve mudar

Não reescreva o código inteiro. Para cada problema, mostre só o trecho corrigido.
Se algo depender de contexto que você não tem, diga isso em vez de supor.

[cole o diff ou os arquivos alterados]
```

### Depurar um erro

```text
Estou com este erro e não sei a causa.

O que eu esperava: [comportamento esperado]
O que acontece: [comportamento real]
Como reproduzir: [passos]
Ambiente: [sistema, versão da linguagem, versões das bibliotecas principais]
O que já tentei: [tentativas e resultado]

Mensagem de erro completa:
[cole o stack trace]

Código relacionado:
[cole o trecho]

Liste as 3 hipóteses mais prováveis, da mais para a menos provável, e diga como testar cada uma antes de mudar o código.
```

Pedir hipóteses com forma de teste, em vez de "corrija o erro", faz o Claude mostrar o raciocínio e deixa você confirmar a causa antes de aplicar qualquer mudança.

### Escrever testes

```text
Escreva testes unitários para a função abaixo usando [pytest / Jest / PHPUnit].
Cubra: caso feliz, entradas vazias ou nulas, valores limite, entradas inválidas e erros esperados.
Antes do código, liste em tópicos os cenários que você vai cobrir.
Não altere a função. Se encontrar um comportamento que parece bug, aponte em vez de "consertar" no teste.

[cole a função]
```

### Exemplo prático: validação de CPF

Um caso comum em sistemas brasileiros, como cadastro de clientes de e-commerce:

```text
Escreva uma função em TypeScript que valide CPF.
Regras: aceitar com ou sem pontuação; rejeitar sequências repetidas (111.111.111-11);
validar os dois dígitos verificadores.
Não use bibliotecas externas. Depois do código, escreva 8 casos de teste em Jest,
incluindo CPFs inválidos. Use apenas CPFs de exemplo, nunca números de pessoas reais.
```

Confira os testes rodando no seu ambiente. Um código que "parece certo" pode errar justamente no cálculo dos dígitos.

### Refatorar sem mudar o comportamento

```text
Refatore este código para melhorar a legibilidade, sem alterar o comportamento.
Restrições: manter a mesma assinatura pública; não adicionar dependências; [outras regras do time].
Mostre o antes e depois só dos trechos alterados e explique cada mudança em uma linha.

[cole o código]
```

Para mais técnicas de como pedir, veja o guia sobre [como melhorar seus prompts](/artigos/como-melhorar-seus-prompts).

## Fluxo sugerido para uma tarefa do dia a dia

1. Descreva o objetivo e as restrições (linguagem, versão, o que não pode mudar).
2. Peça primeiro um plano ou pseudocódigo, não o código final.
3. Aprove ou corrija o plano e só então peça a implementação.
4. Peça os testes junto com o código.
5. Rode tudo no seu ambiente e cole de volta as falhas, com a mensagem completa.
6. Antes de fazer o commit, peça uma revisão crítica do resultado final ("o que pode quebrar em produção?").

Se a tarefa exigir que você cole muitos arquivos a cada rodada, é sinal de que o Claude Code resolve melhor.

## Artifacts: protótipos que rodam no chat

Quando o objetivo é uma ferramenta pequena e independente, como uma calculadora de frete, um formulário ou um painel simples, o Claude pode criar um Artifact, que aparece ao lado da conversa e pode ser testado ali mesmo. Todos os planos criam Artifacts no chat. Veja exemplos no [guia de Artifacts do Claude](/artigos/claude-artifacts-recursos).

## Limitações e erros comuns

- **Bibliotecas e APIs mudam.** O Claude pode sugerir uma função que mudou de nome ou foi removida numa versão recente. Informe a versão que você usa e confira na documentação oficial da biblioteca.
- **Ele só vê o que você mostra.** Sem o resto do projeto, a resposta pode assumir coisas erradas sobre tipos, rotas ou o esquema do banco.
- **Código plausível não é código correto.** Rode os testes e revise a lógica, principalmente em cálculos financeiros, autenticação e permissões.
- **Segurança exige revisão humana.** Peça explicitamente uma revisão de segurança e, em sistemas críticos, faça também uma revisão com alguém do time.
- **Conversas muito longas perdem foco.** Quando o assunto mudar, abra uma conversa nova com um resumo do que já foi decidido.

## Privacidade: o que evitar colar

Nos planos Free, Pro e Max, as conversas podem ser usadas para treinar modelos se a opção Model Improvement estiver ligada; nos planos comerciais (Team, Enterprise e API), não há treinamento por padrão, segundo a [central de privacidade da Anthropic](https://privacy.claude.com/en/articles/10023580-is-my-data-used-for-model-training). Mesmo assim, siga a política da sua empresa e nunca cole credenciais, arquivos `.env` ou dados pessoais de clientes. Os detalhes estão no guia [Claude e segurança de dados](/artigos/claude-seguranca-privacidade-dados).

## Quando NÃO usar o chat para código

- Mudanças que tocam muitos arquivos de um projeto grande: use o Claude Code.
- Código sob contrato de confidencialidade que proíbe o uso de ferramentas externas.
- Quando você está aprendendo e ainda não sabe revisar a resposta: peça explicação e escreva o código você mesmo.
